Document Embedding Studio

A local-first application for building the ingestion side of a RAG (Retrieval-Augmented Generation) system — the part that lets an AI answer questions using your own documents.

View on GitHub

What

Drop in PDF, DOCX, Markdown, or plain-text files → the app extracts the text, splits it into overlapping chunks, embeds every chunk with a local AI model, and stores vectors in a persistent ChromaDB collection. From there: semantic search, or a BYOK chatbot that answers grounded in what's indexed. A live panel shows CPU/memory for the app's own Docker containers.

My role

Built the ingestion pipeline, then layered on BYOK chat and the live container-monitoring panel; built in pair-programming with an AI assistant (Claude).

Quality

70 tests covering chunking, document loaders, and the full ingest/search/chat/monitor API. Chat and container-monitor tests mock the outbound LLM call and the Docker socket, so the full suite runs offline.

Status

MIT · source on GitHub. No hosted demo — it needs a long-running Python process and direct Docker-socket access that managed hosting platforms don't expose; runs locally via Docker.

Why this exists

Most "RAG demo" projects stop at a single script calling an API. This one is built like a real application: a proper pipeline with validation at every step, a UI to actually use it, and no paid API key required for the core loop — embedding and retrieval run entirely on your own machine, using a local sentence-transformers model. The optional chat layer is explicitly bring-your-own-key, so nothing is sent anywhere unless you choose it.

Highlights

  • Natural-boundary chunking. When a character-window chunk would end mid-word, the cut is pulled back to the nearest paragraph break, then sentence ending, then line break, then whitespace — so chunks stay close to the configured size without cutting words in half.
  • Multi-stage Docker builds. The frontend's Dockerfile builds in a Node stage and ships only the production output in a slim runtime stage, so dev dependencies never reach the final image.
  • Named volumes for real persistence. Vectors and model weights survive docker compose down via named volumes (chroma-data, hf-cache), since a container's own filesystem is ephemeral by design.
  • Containers found by label, not by name. The live container-monitor panel locates its own two containers via a studio.monitor label, so it works regardless of the folder or Compose project name.
  • The Docker-socket trade-off is documented, not glossed over. Giving the backend read access to the Docker socket is a real privilege — anything with socket access can, in principle, control any container on the host. Stated plainly, with the reasoning for why it's acceptable for a local single-user setup.

How it was built

FastAPI backend with a strict separation of concerns — extraction, chunking, embeddings, and vector storage are independent modules composed by a single pipeline function. Embeddings run locally via sentence-transformers (all-MiniLM-L6-v2, 384 dimensions, no API key), stored in ChromaDB. The frontend is Next.js (App Router) with strict TypeScript. BYOK chat supports OpenAI, Anthropic, or Gemini — the key is kept only in the browser tab's session storage, never written to disk or logged server-side.
