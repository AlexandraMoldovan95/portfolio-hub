Document Embedding Studio

Search your own files by meaning, not just by exact words, and ask questions that are answered from what is in them, with the source passages listed. Everything runs on your computer; nothing leaves it unless you add your own key for the optional chat. The demo uses three invented sample documents: try a search, then ask a question.

What it does

You drop in PDF, Word, Markdown or text files. The app reads them, splits them into small overlapping pieces and lets you search the pieces by meaning or ask questions about them.

The product: what the app does, how it handles files and keys, and what the tests must cover. The code was written with an AI assistant (Claude).

How it works, and what I checked

An AI answering from memory can sound sure and be wrong. Here you can check each answer against the passages it came from.

Search by meaning

A normal search finds the exact words you typed. Here, the app turns each piece of a document into numbers that capture its meaning, using a small AI model that runs on your own machine, so a question can find a passage that uses different words. No paid key is needed for this part.

Answers that show their sources

In the optional chat, the best-matching passages are sent to the AI provider you choose (OpenAI, Anthropic or Gemini) with the instruction to answer only from them. The passages are listed under the answer. You bring your own key; it stays in that browser tab and is not written to disk.

Decisions I made and why

  • Files are checked three ways before they are read: the extension, the declared file type and the first bytes of the file. A renamed .exe is refused even if it says it is a PDF.
  • Pieces overlap, and cuts avoid the middle of a word. A cut moves back to a paragraph break, then a sentence end, so an idea is less likely to be split in two.

What the tests cover: 72, counted

I counted 62 test functions in the repo's backend tests folder. Some run several times with different inputs, which makes 72 test cases. Their coverage:

  • Splitting text, including the edge case where the overlap is one character smaller than the piece, which must not loop forever.
  • Reading each file type, and refusing wrong, empty, damaged or renamed files.
  • Uploading, searching and collections, including that stored data survives a restart.
  • Chat with all three providers and a wrong key, and the container panel. The AI call and Docker are replaced by stand-ins, so the suite runs offline.

They last ran on 25 November 2026, all 72 passing. Nothing runs them automatically on every change yet.

What testing and reviews found

  • Another website could read the container panel. The panel shows the app's own Docker containers over a WebSocket, and the browser's usual cross-site protection (CORS) doesn't cover WebSockets, so any site open in the same browser could have read that list. The server now refuses unknown origins (25 November 2026). Two tests cover it, and with the check removed on a scratch copy the refusal test fails, so it really guards the fix.
  • The app was reachable from other devices on the network. The Docker setup now publishes its ports on this computer only.
  • A wrong test count in my own docs. The README said 71. Counting the test functions and their repeated cases gave 70, and I corrected it everywhere. Two later tests brought it to 72.

How it's built

Two parts that talk to each other: a Python backend (FastAPI) that does the work, and a web page (Next.js with TypeScript) you use in the browser. Both run in Docker, a way to package an app so it runs the same on any computer.

  • The pipeline is separate steps. Reading, splitting, turning text into numbers ("embedding", done with a small local model) and storing them (in ChromaDB, a database made for this) are independent parts joined by one function. The diagram at the top of the page shows the flow.
  • Data survives restarts. The stored numbers and the downloaded model live in named Docker volumes, because a container's own storage is thrown away when it stops.
  • The privilege trade-off is written down. To show container stats, the backend gets read access to the Docker socket, which in principle can control any container on the machine. The README says so and why it is acceptable for a single-user setup on your own computer.

What I haven't done yet

  • The live demo is not the real app. It runs on sample data and scores matches by shared words, with no AI model. The real app needs a long-running Python process and Docker access that simple hosting doesn't give, so it only runs on your computer.
  • The chat tests use stand-ins for the AI providers. I haven't tested against the real services, and I haven't measured how good the search results are.
  • The backend container still runs as root. Scanned PDFs are refused, not read with OCR (text recognition from images). Uploading the same file twice creates a second copy.
