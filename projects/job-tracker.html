PWA · Supabase

Job Tracker

A job application tracker where every user's data stays completely private from every other user - not hidden by the interface, but actually walled off at the database level, so even a buggy or tampered client couldn't see someone else's applications. That protection comes from a Postgres/Supabase feature called Row Level Security. It runs on plain HTML/CSS/JS with real authentication, no framework, no build step.

Live demo View on GitHub

What it does

Auth (email/password), companies, applications with status tracking, a dashboard with response-rate and top-company stats, multi-version resumes exportable to a formatted HTML/PDF file, a self-service "Delete account" that removes the account and everything in it, an installable PWA with a proper offline fallback, and a "Support the project" button that opens a Stripe checkout page in test mode, just to show the flow.

My role

Product idea, UX, and the security model (RLS policy design); built in pair-programming with an AI assistant (Claude).

Quality

Data isolation was tested, not assumed: a second test account sees none of the first account's data, can't rename or delete it (0 rows affected), and can't save a row in someone else's name (HTTP 403) - re-checked on the live project in November 2026. Account deletion is tested end to end: 7 API checks and 13 UI checks.

Status

Live · MIT · source on GitHub.

Why this exists

A job tracker looks like a simple CRUD problem, but it's a good vehicle to demonstrate something that's easy to get wrong: real multi-user data isolation, enforced where it actually matters - the database - not just hidden in the UI. Every row a user creates is tied to their own auth.uid() through Postgres Row Level Security policies, so even a broken or malicious client can't read another user's data.

Design case study: a neon theme that still reads like a tool

A job tracker is a plain data app, the kind that usually looks generic. I wanted this one to be memorable, but it's also a tool you open every day to read your own data, so the look can't get in the way of reading.

Start from a style, then tone it down

I started from an existing vaporwave/outrun style direction - near-black purple, neon cyan, magenta and orange, skewed buttons, CRT scanlines, Orbitron and Share Tech Mono - and translated it into plain CSS to match the no-framework app. Then I adjusted it for real data: the scanlines are subtler than in the original spec, because the list text got hard to read; the button slant went from 12° to 6° (3° on the small list buttons), because a strong slant broke small buttons visually; status badges became neon outlines instead of filled pills; and error messages moved from light grey on neon red to a black background.

One thing I deliberately kept out of the theme: the CV export. It stays plain and professional, because that file goes to real employers.

After the reviews (November 2026)

Reviewers pointed at the login screen. A visitor without an account had to find "Login demo" under the real login, with the same weight; the demo is now the first, filled button, with the real login below "or use your account". The inputs were pure black boxes on the purple card ("black holes", one reviewer said); they now sit on the purple surface with a thin outline and keep the magenta neon underline. Placeholder text went from 1.97:1 to 6.56:1 contrast; typed text stays at 13.8:1.

What I haven't done yet

  • No usability testing with job seekers. The changes above came from my own use and from reviews.
  • Some labels on phones are still small (about 11 px).

Highlights

  • A modal UX bug fixed properly. Modals used to close on any click outside them, so selecting text inside a field (a drag that ends over the backdrop) could silently discard unsaved input. Fixed by removing backdrop-close entirely, with a visual cue when changes are unsaved.
  • Isolation verified with a second account, not assumed. A dedicated test account confirmed it saw zero companies and zero applications from the first account.
  • A payment flow that's demonstrated, not faked. "Support the project" opens a real Stripe Payment Link in test mode, so a reviewer sees an actual Stripe checkout screen rather than a mockup - but it's clearly scoped as a demo: test mode only, no live key anywhere in the code, no backend order record, and no webhook, so no real charge ever happens.
  • Database-level protection on every table, not just app-level checks. Enforced by Postgres itself through a feature called Row Level Security, so a user can only select, insert, update, or delete their own rows - even if the app code were buggy or bypassed.
  • Extra browser-side security headers, not just HTTPS. A real HTTP Content-Security-Policy header - via Netlify's _headers file, not just a meta tag, which can't carry frame-ancestors - plus X-Frame-Options and a locked-down Referrer-Policy, guarding against clickjacking and script-injection attacks.
  • An honest PWA (installable app) that doesn't fake offline support. The service worker - the background script that makes a web page installable like a native app - gives it a proper offline fallback screen, but deliberately doesn't cache the app shell itself: since the app is live-data-dependent anyway, caching it would just produce the classic bug of users stuck on a stale version after a deploy.

How it was built

No framework, no bundler - HTML5/CSS3/vanilla JavaScript talking directly to Supabase (Postgres + Auth + Row Level Security), loaded from a pinned CDN URL with Subresource Integrity. The Supabase key shipped to the client is the publishable key, designed to be public - the real access control is the RLS policies, not key secrecy. The visual direction (vaporwave/outrun - cyan and magenta on near-black, a CRT scanline overlay) was a deliberate choice to make a CRUD app memorable rather than generic.
